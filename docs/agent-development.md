# 通用 Agent 开发技术指南

本文面向开发多用户、多 Agent 平台的工程师。前三个案例取自 Codex、Pi coding agent 和 Claude Code 的公开接口与官方设计说明。后文以“定位测试失败并提出修复”为例，给出语言无关的平台设计。案例说明产品公开的行为，平台设计部分则给出可自行实现和验收的方案。

## 1. 三种 Agent 如何组织执行

### Codex：把执行循环封装为应用可驱动的服务

Codex 将模型外层的执行系统称为 **harness**。它管理跨轮上下文、工具执行、沙箱、审批及进度事件。通过 app-server 接入时，宿主先创建或恢复 thread，再启动 turn。一次 turn 中可以出现多项活动，界面可以逐步显示输出、响应审批，或中断执行。收到轮次结束通知后还要检查终态，以区分成功、失败和中断。一次性后台任务可用 exec；需要在自己的产品中呈现执行过程时，app-server 提供更细的控制。[OpenAI 官方设计说明](https://developers.openai.com/blog/codex-as-a-platform) · [协议交互示例](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

**值得借鉴的边界**是把产品会话、运行时 thread 和单次 turn 分开建模。这样用户刷新页面时可以重新订阅同一次运行，业务工具仍由宿主按当前用户授权，聊天界面也无需自行解释终端文本。

### Pi：把可组合的会话作为嵌入入口

Pi 的 SDK 以 `createAgentSession()` 创建执行会话。宿主可以指定工作目录、工具、模型和会话管理器，订阅事件，再调用 `prompt()` 运行任务。会话可保存在内存或持久化为 JSONL，支持继续和分支。工作目录同时影响项目资源发现和内置工具的路径。宿主也可以通过 RPC 驱动独立的 Pi 子进程，从而跨语言集成。[Pi SDK](https://pi.dev/docs/latest/sdk) · [Pi 官方文档](https://pi.dev/docs/latest)

**值得借鉴的边界**是把“会话怎样保存”和“Agent 如何完成当前任务”分开。例如离线评测可用内存会话；交互式开发可保留历史，在一次危险修改前分支试验。会话分支只复制对话路径。如果两个分支都要修改代码，还需给它们独立的工作目录或工作树。

### Claude Code：围绕取证、行动和验证组织工具与子任务

Claude Code 将工作过程描述为收集上下文、采取行动、验证结果。处理测试失败时，读取断言和实现属于取证，编辑代码属于行动，重新运行测试提供验证；测试继续失败便触发下一轮取证。专用 subagent 可以用自己的上下文、指令和受限工具集调查问题，再将结果返回主会话。大量搜索输出由调查者消化，主会话保留结论和证据位置。需要从应用中使用这套执行能力时，可接入 Claude Agent SDK。[Claude Code 工作原理](https://code.claude.com/docs/en/how-claude-code-works) · [子 Agent](https://code.claude.com/docs/en/sub-agents) · [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)

三个案例分别展示了**宿主怎样驱动运行、会话怎样嵌入、子任务怎样分工**。同一平台可以同时采用这些设计。下文的状态名和数据模型为平台设计示例，接入时需映射到所选 Runtime 的实际协议。

## 2. 技术栈与所需技能

| 技术领域 | 开发者需要掌握什么 | 何时引入 |
|---|---|---|
| Web 框架与流式通信 | 身份中间件、请求校验、异步提交、SSE 或 WebSocket、断线续订 | 多用户入口。HTTP 返回任务 ID，客户端独立消费执行事件 |
| 模型 API 与结构化输出 | 流式响应、工具声明、调用 ID、停止原因、Token 预算、限流退避 | 每个 Agent 都需要理解；使用成熟 Runtime 时由适配层处理供应商差异 |
| 数据库与对象存储 | 事务、唯一约束、事件顺序、版本校验、二进制产物和生命周期 | 数据库存会话、授权和运行状态；大日志、文件、补丁按需存为产物 |
| 工具与协议 | 参数模式、进程调用、远程鉴权、超时、重试和幂等 | 内置函数适合进程内操作，MCP 适合接入可复用能力，A2A 适合委托独立 Agent |
| 检索与知识工程 | 文档解析、切片、全文检索、向量检索、排序、引用和权限过滤 | 有持续更新的外部语料时引入；代码任务也可直接按符号、路径或文本搜索 |
| 并发与任务调度 | 取消传播、并行读、写冲突、任务队列、租约和背压 | 长任务、多 Worker 接管、并行子任务 |
| 安全执行与凭据管理 | 操作系统权限、沙箱、网络策略、短期凭据、授权与审批 | 工具可读私有数据、执行命令或修改外部系统时 |
| 可观测性与评测 | 关联调用链、统计时延和成本、构建可重复任务、校验最终状态 | 联调和版本升级；同时评估任务完成率与越权、重复写入等错误 |

### 2.1 模型适配

接入模型时分开配置三个概念：**接口类型**决定消息和工具调用怎样编码，**API 版本**决定服务端采用哪一版协议，**模型 ID**选择实际执行推理的模型。例如，OpenAI 的两个接口路径都含有 `v1`，但从 Chat Completions 切到 Responses 时，请求和结果解析都要调整。

| 厂商 | 常见接口类型 | 版本与适配要点 |
|---|---|---|
| OpenAI | Chat Completions（`/v1/chat/completions`）与 Responses（`/v1/responses`） | 前者发送 `messages`、读取 `choices`；后者发送 `input`、读取 `output` 项，函数调用及其结果分别表示为独立项。迁移时要同时调整工具回填和流式事件解析。[官方迁移指南](https://developers.openai.com/api/docs/guides/migrate-to-responses) |
| Anthropic | Messages（`/v1/messages`） | 除路径外，还通过请求头 `anthropic-version` 指定协议日期，例如 `2023-06-01`。模型由 `model` 另行选择；工具往返通过 `tool_use` 和 `tool_result` 内容块配对。[版本说明](https://platform.claude.com/docs/en/api/versioning) · [Messages 接口](https://platform.claude.com/docs/en/api/messages/create) |
| Google Gemini | `generateContent`、流式 `streamGenerateContent`，以及 Interactions API | 路径中的 `v1` 表示稳定版，`v1beta` 提供仍可能变化的功能。选定接口后再核对目标版本支持的功能，并在 SDK 中显式指定版本。[版本与能力对照](https://ai.google.dev/gemini-api/docs/api-versions) |
| DeepSeek | OpenAI Chat Completions 兼容格式、Anthropic 兼容格式 | 根据客户端协议选择对应的基础地址。模型别名可以继续有效，但背后的模型实现可能更新；沿用同一调用方式时，也应回归验证工具行为。[官方接入说明](https://api-docs.deepseek.com/) |

**在 Agent Loop 中**，适配层将厂商响应转换为统一的“文本增量、工具调用、结束原因、错误”事件，并把执行结果按原调用标识回填。切换厂商或版本时，可先回放一个最小场景：模型请求读取日志，工具返回指定行，模型据此作答。这样一次即可验证流式解析、调用配对与轮次收尾。

## 3. 核心术语

| 名词 | 工程含义 |
|---|---|
| Agent、模型、Runtime | 模型生成下一步行动或答复；Agent 结合模型、指令和工具承担职责；Runtime 驱动执行、处理工具结果并管理生命周期。 |
| Session / Thread、Turn、Step | Session 或 Thread 保存持续工作历史；Turn 表示一次用户输入引发的处理；Step 是其中一次推理、调用或执行步骤。各框架对 turn 的计数可能不同。 |
| Event、Message、Artifact | Event 记录发生的事实，Message 是对话内容，Artifact 是可引用的文件、补丁或报告。可从事件生成界面消息，一条消息也可能由许多流片段组成。 |
| Context、Token、Compaction | Context 是本次请求实际提供给模型的信息；Token 是计量单位；Compaction 通过摘要等方式压缩历史，为后续推理预留空间。 |
| Tool call、Skill、Hook | Tool call 请求执行带参数的操作；Skill 封装可按需加载的任务说明和资源；Hook 允许宿主在调用前后等生命周期节点执行确定性逻辑。 |
| MCP、A2A | Model Context Protocol 让应用发现和使用工具、资源等能力；Agent2Agent 支持独立 Agent 之间交换消息、委派和跟踪任务。本地父子 Agent 也可直接用 Runtime 的委派机制。 |
| RAG、Embedding | 检索增强生成（RAG）在回答前取回相关资料；Embedding 将内容编码为向量，用于相似度召回。全文检索也可以驱动 RAG。 |
| HITL、Checkpoint、Sandbox | HITL 指人在执行中补充信息或审批；Checkpoint 是可恢复的执行位置及状态；Sandbox 通过系统机制约束可访问的文件、进程或网络。 |

## 4. 模块划分与信息流

### 4.1 参考架构与数据所有权

~~~text
客户端 → 会话 API → 轮次记录与调度队列 → Worker → 模型
           ↑                           ├─ 上下文组装器 → 历史 / 记忆 / 知识库
           └── 订阅 ← 有序事件日志 ←───┤
                                       └─ 工具执行器 → 本地沙箱 / MCP / A2A
                                           └─ 检查点 / 人工待办 / 产物
~~~

会话 API 确认主体和资源归属，Worker 拥有本次执行权，模型提出下一步动作，工具执行器负责实际授权与执行。受理轮次与写入调度发件箱可放在同一事务中，后台再投递任务，避免 API 已返回成功却没有 Worker 收到任务。界面从事件构造进度视图；外部写入结果则以业务系统回执为准。

### 4.2 知识库的三种组织方式

| 方式 | 写入与查询路径 | 适用问题与代价 |
|---|---|---|
| 结构化查询与全文检索 | 对业务字段建索引，文档建立倒排索引；按主键、关键词、符号或路径定位原文 | 查构建状态、错误码、函数定义时容易验证；跨文档归纳需要后续处理 |
| 分块 RAG | 按章节切片，保存来源、版本和权限，以关键词和向量分别召回，合并排序，再按预算取证 | 适合持续更新、提问方式多变的语料；分块截断前提或漏召回时，模型很难补全证据 |
| LLM Wiki | 保存原始资料，由模型持续维护主题页、索引、交叉链接与修订记录；查询先读综合页，再回查依据 | 适合反复跨资料归纳的任务，把部分综合成本提前到入库阶段；页面需要处理冲突、维护成本和过期结论 |

**Wiki 的实现闭环。** 以持续收集测试故障为例，摄入（ingest）时把新故障关联到已有主题页，补上发生条件、反例和原始日志引用；查询（query）时沿索引找到相关主题、核实来源，将值得复用的综合结论写回；巡检（lint）时查找断链、过期结论、互相矛盾的页面和缺少依据的陈述。Wiki、检索和实时查询可以组合：主题页解释“为什么经常失败”，原日志验证“那次如何失败”，CI 接口回答“本次是否通过”。[Karpathy 的 LLM Wiki 原始设计](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

**派生数据的权限与更新。** 用来源 ID 和修订号去重入库，每段结论保留原文定位；并发改页时校验页面版本。若两个权限范围不同的来源合成一页，可按权限域分别生成，或仅向同时有权读取两份来源的人开放整页。撤权时先阻断访问，再沿来源依赖关系重建派生页、索引和缓存。验收时撤下一份关键来源，同时检查全文查询、向量召回与 Wiki 导航三条路径。

### 4.3 记忆系统的读写设计

| 类型 | 保存什么 | 如何读写 |
|---|---|---|
| 工作记忆 | 当前目标、待办、未完成的调用 | 每步更新当前任务状态；暂停时进入检查点 |
| 情景记忆 | 某次排障尝试、条件、结果与证据 | 任务结束时提取；以后按项目、时间和语义检索相似经历 |
| 语义记忆 | 有来源的事实、明确偏好及适用范围 | 先按主体与键精确读取；变更时记录来源、生效时间和旧版本 |
| 程序性记忆 | 已验证的排障步骤、项目规程或 Skill | 按任务加载，变更经过评审和回放验证 |

最小实现是带作用域的键值表；事例多到无法按键定位时再加检索索引。自动提取可走“生成候选 → 核实来源与作用域 → 去重或修订 → 生效”。例如“这次跳过集成测试”只写本轮工作记忆；“项目测试命令已改”须核对项目配置后再更新共享记录。读取先过滤权限、失效与撤销状态，再按相关度和时间排序。用跨会话召回、另一用户无法召回、显式纠正后旧记录不再生效三个场景验证读写闭环。

### 4.4 上下文压缩与恢复

一次请求可分配给历史与证据的预算，等于模型窗口减去固定指令、工具声明、预留输出及安全余量。每轮按实际输入估算，大工具回包后重新检查。不同任务的日志量、调用次数不同，触发阈值应通过任务回放校准。

| 策略 | 如何实现 | 主要取舍 |
|---|---|---|
| 滑动窗口 | 以完整交互组为单位保留最近历史，单独保留仍生效的用户约束 | 速度快，容易遗漏早期决定 |
| 输出外置 | 完整日志写入产物库，只回填退出码、关键行和可按行号读取的引用 | 节约最多的是冗长工具输出；必须允许回查原始证据 |
| 滚动摘要 | 在已完成的步骤边界总结旧前缀，保留目标、事实、假设、待办和证据位置，拼接未经改写的近期事件 | 反复总结会累积偏差；精确 ID、审批参数和未决调用另存结构化状态 |
| 检索式组装 | 按当前目标从旧历史、记忆和知识库选择少量相关片段 | 适合跨度大的任务；精确字段按键读取，避免只靠语义召回 |
| 子任务隔离 | 调查者独立消化大量搜索结果，仅返回结论与可核验引用 | 主会话更紧凑，但需承担额外推理成本，并保留追查细节的路径 |

保存摘要时记下会话分支、覆盖到的事件序号和摘要版本。恢复时拼接“摘要 + 边界后的完整事件”，防止遗漏或重复；工具请求与结果必须仍可配对。使用提供方原生 compaction 时按其协议保存和传回压缩产物，应用另存审批、授权和执行检查点。验收长任务时要比较压缩前后是否保留同一验收条件、能否重现失败，并能继续原来的待办。[OpenAI 官方 Codex 压缩说明](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

### 4.5 Local tool、MCP、A2A 与 Skill

“本地”描述执行位置，MCP 描述能力访问协议，A2A 描述独立 Agent 的协作协议。本地子进程也可以是 MCP server。选型时先确定要委托的是一个明确定义的操作，还是一项由对方自行组织步骤的任务。

| 方式 | 发现与调用 | 权限与生命周期 | 例子 |
|---|---|---|---|
| Local tool | 宿主注册函数或可执行程序，定义参数、结果和错误结构 | 函数共享进程权限；子进程需显式约束路径、环境、网络、时限和输出 | 在授权工作树运行指定测试，返回退出码和日志引用 |
| MCP | Host 内的 client 连接 server，协商能力，用 tools/list 发现工具、tools/call 调用；可经 stdio 或 HTTP 接入 | 宿主决定可见工具，服务端校验资源权限；除工具外还能提供资源、提示模板 | CI 服务暴露按构建号取日志的操作，供多个客户端复用 |
| A2A | 读取 Agent Card 获取能力说明，发送消息；对方可直接回复或返回可跟踪的 Task | 远端管理执行过程，本地保存远端任务 ID，跟踪补充输入、终态及产物 | 委托兼容性调查，由远端测试多个版本并返回报告 |

可让 A2A 调查者内部使用 MCP 读构建日志，再用本地工具复现。宿主记录每一跳的调用者、能力范围、操作 ID 和超时；跨服务中断后先按远端任务 ID 查状态。流式更新与取消等可选能力以远端声明为准。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture) · [A2A 官方规范](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)

**Skill 的渐进式加载。** 发现阶段只读取名称与描述，匹配任务后才加载 SKILL.md 正文，附带脚本与参考资料按需读取。例如“测试故障排查”Skill 可以约定先找上次成功构建、再比较依赖，实际读取 CI 或执行脚本时仍经同一授权路径。版本化说明与资源可以独立演进，也减少常驻提示占用。[Agent Skills 规范](https://agentskills.io/specification)

### 4.6 多 Agent 编排

 把能独立调查且有明确交付物的工作委派出去。例如主 Agent 让只读子 Agent 定位失败断言，并要求返回文件位置、复现命令和证据；主 Agent 负责决定修改与验收。委派时传递任务所需上下文、能力范围、期限和预算。独立调查可并行，同一文件的修改需协调所有者或使用独立工作树。取消父任务时传播取消，子任务失败时由父任务决定重试、降级或报告缺失证据。

## 5. 完整 Agent loop

| 步骤 | 运行时与宿主的动作 | 测试修复示例 |
|---|---|---|
| 1. 受理 | 认证用户，校验会话与工作区归属，为本次输入分配 turn ID，记录目标与预算 | 用户请求修复某条失败测试 |
| 2. 恢复与组装 | 读取会话检查点，选择模型、指令、工具和相关上下文 | 加载项目测试说明和上次运行的日志引用 |
| 3. 推理与分流 | 调用模型并消费流事件；根据完整响应和停止原因区分最终答复、工具调用、中断和错误 | 请求读取测试文件与实现 |
| 4. 执行前检查 | 校验完整参数和权限，独立只读请求可并行；需要审批时保存待办、释放执行资源 | 读取文件可直接执行，而写入受保护目录触发审批 |
| 5. 行动与回填 | 执行工具或委派子任务，将结果与对应 call ID 一起写入事件历史 | 回填断言差异、补丁结果和测试退出码 |
| 6. 迭代与验证 | 在期限、步数和成本预算内返回步骤 2；依据新证据修正计划 | 测试仍失败就继续调查，测试通过后检查改动范围 |
| 7. 收尾 | 持久化终态、答复与产物引用，发送完成事件，释放资源 | 返回修改文件、实际执行的测试及结果；未运行的检查明确标出 |

**等待、取消和崩溃是三条不同的路径。** 等待审批时记录用户、工作区、调用 ID 和具体参数，收到匹配答复后继续同一轮。取消时停止派发新调用，并处理已启动的子任务。进程崩溃后先读取检查点：若“工具已提交”有记录而结果缺失，先查询外部操作状态；无法确认且重复执行有风险时，将控制权交回用户。浏览器断流仅影响订阅，客户端可以按事件游标补读状态。


### 5.1 Session、Turn 和一次执行尝试

用户先说“查出失败原因”，再说“按方案修复”，构成同一 session 的两个业务 turn。第二个 turn 可能有多次模型推理、三次工具调用、一次审批和一次 Worker 重启。审批答复按 approval_id 回到原 turn；如果把它当作新的修复请求，就可能重复生成补丁。

| 对象 | 建议关联 | 开发时要回答的问题 |
|---|---|---|
| Session | session_id、tenant、owner、workspace、runtime_thread_id | 谁能继续这段历史？从哪个事件分支？ |
| Turn | turn_id、session_id、request_id、目标、状态、预算 | 这次用户意图完成了吗？重复提交能否返回同一轮？ |
| Attempt | attempt_id、turn_id、执行租约、检查点 | 哪个 Worker 当前有权推进？重启后由谁接管？ |
| Tool call | call_id、turn_id、参数、结果、外部幂等键 | 这条结果属于哪次请求？恢复时有无重复副作用？ |
| Event | event_id、turn_id、序号、类型、主体 | 客户端断开前看到哪里？回放时怎样去重？ |

同一 turn 重试时更新 attempt，保留业务轮次与逻辑操作的幂等键。收到运行中的用户输入时应显式区分三类消息：新目标进入队列，纠正指令在安全步骤边界注入，审批答复恢复指定检查点。适配层保存平台标识与 Runtime 标识的映射，避免用一次模型响应的结束代替整轮完成。

### 5.2 HITL 的可恢复状态机

以“批准把补丁写入共享分支”为例，决定必须绑定到具体操作和参数。人工澄清也可使用待办机制，但“补充哪些测试要跑”和“授权写入共享分支”应具有不同的待办类型。

~~~text
Running → WaitingForApproval → Approved → Executing → Running
                             → Rejected / Expired → 重新规划或结束
~~~

1. **暂停。** 在副作用发生前，事务性保存检查点、待办和轮次状态，再发送通知。待办记录允许审批的人、turn_id、call_id、目标分支、补丁内容哈希、到期时间和版本。Worker 可释放资源。
2. **展示。** 界面显示准确差异、目标和影响，并支持拒绝。刷新后按身份重新读取待办。若参数被修改，为新的操作内容建立新的请求。
3. **裁决。** 服务端验证身份、有效期、权限范围和请求版本，以条件更新一次性消费 pending 状态。重复点击返回已有决定。多个并行调用各自绑定待办，仅在依赖项齐备后推进。
4. **恢复。** Worker 取得新的执行权，再校验目标版本、权限和参数仍与审批一致。使用稳定幂等键执行操作，落盘结果并回填原 call_id。拒绝或过期时将该结果送回循环，由 Agent 重新规划或结束。
5. **核对副作用。** 若已批准但尚未提交写入，可继续执行；若已提交但缺少回执，先向下游查询。下游无法去重或查证时记录“结果未知”，交由人工核实。审计记录串起申请、裁决、参数版本与最终结果。

LangGraph 的 interrupt 提供了可对照的实现：用持久化 checkpointer 和 thread 标识保存状态，通过恢复输入继续执行。包含 interrupt 的节点在恢复时会从头运行，因此中断前的副作用应可重复，或拆到单独的可核对步骤。验收时覆盖待批重启、重复批准、拒绝、目标版本变化及写入成功但回执丢失。[LangGraph 中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 6. 怎样接入成熟 Runtime

先决定宿主要控制哪些动作，再选接入层。后台批处理通常只需输入、终态及产物；交互产品还需要中途审批、取消、进度展示与恢复。跨语言宿主可以通过进程协议对接 Codex app-server 或 Pi RPC。要直接配置会话管理器和工具，可采用 Pi SDK；要沿用 Claude Code 的执行能力和子 Agent 定义，可采用 Claude Agent SDK。接入前逐项核对所选接口支持的功能。[Codex 集成层次](https://developers.openai.com/blog/codex-as-a-platform) · [Pi 接入方式](https://pi.dev/docs/latest) · [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)

建议宿主维护三份映射：业务会话到 Runtime 会话、平台轮次到运行实例、审批单到工具调用。适配层将原始事件映射为“文本增量、工具开始、工具结果、需要输入、运行结束”等产品事件，同时保留原始事件 ID 和终止原因。权限检查放在受信任的宿主或工具服务中。**恢复会话**表示可以沿用已有历史，**恢复中断操作**还需要持久化步骤、记录副作用并支持去重，两者应分别验收。

## 7. 多用户、多会话隔离

| 隔离对象 | 实施位置 | 重点验收 |
|---|---|---|
| 租户与用户数据 | 认证层得到主体身份；数据库、检索、缓存和对象存储都按所有权或授权范围访问 | B 持有 A 的会话、文件或引用 ID，仍无法读取、订阅或修改 |
| 会话与执行 | 按会话保存历史和游标；写操作采用版本检查或单写者策略，多副本使用带版本的租约 | 两个标签页同时提交时顺序明确；旧 Worker 失去租约后无法覆盖新结果 |
| 工作目录与进程 | 每次运行绑定授权目录和执行身份，按需要启用容器或系统沙箱约束文件、网络和子进程 | 同一用户的实验分支互不覆盖，不同用户无法通过绝对路径、符号链接或子进程读取对方文件 |
| 工具与远程身份 | 工具从受信任上下文取得身份，按用户或任务签发最小权限凭据；子 Agent 只能继承获准能力 | 低权限用户无法借共享 MCP 服务、A2A 委派或过期审批扩大权限 |
| 记忆、日志与成本 | 明确用户、项目和会话作用域；敏感字段脱敏；按用户和任务限制并发、Token、时间 | 跨会话偏好只对正确用户生效，故障日志不暴露密钥，循环耗尽预算后能退出 |

## 8. 开发验收与本仓库参考

第一条端到端用例可只覆盖一个用户、一个会话、一个只读工具：提交问题，看到工具开始和结果，得到可核验的答复。随后依次加入写入审批与拒绝、工具执行后断线、长上下文压缩、子任务取消、两个用户访问同一资源。升级模型或 Runtime 时回放同一批任务，比较实际文件状态、工具副作用次数、来源引用、时延和成本。聊天文字只是验收材料之一。

本仓库可以作为上述分层的一个实现样本。对照阅读时可看 [Runner 装配与事件消费](../internal/service/runtime.go)、[持久化会话适配](../internal/service/adapter/session_service.go) 和 [中断恢复入口](../internal/service/recovery.go)。正文的平台方案可独立于这些实现采用。
